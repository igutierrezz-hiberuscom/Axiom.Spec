# 03 Criterios de Aceptación

## Criterios de aceptación

Los criterios son verificables contra un Launcher real sobre loopback y seams del runner/helper. Ninguno se considera satisfecho por documentación o mocks aislados si el wiring HTTP/frontend no existe. La aceptación de este incremento no certifica release CI ni sustituye la matriz final del incremento 5.

### Happy path

- **CA-LSI-01 — Secuencia y gate.** Dado el plan de implementación, cuando comienza el trabajo, entonces existe evidencia de compatibilidad de los incrementos 1, 2 y 3 y se registra `GO`; si falta su API headless o helper, se registra `STOP` y no se crea un motor alternativo.
- **CA-LSI-02 — Bootstrap no bloqueante.** Dado un remoto que tarda más que el deadline, cuando se abre `/launcher/`, entonces bootstrap, sesión, assets y status local responden sin esperar al fetch y el resto del Launcher permanece utilizable.
- **CA-LSI-03 — Refresh canónico.** Dado un remoto Git bare local autorizado con una release posterior, cuando termina el refresh de arranque, entonces se actualizan evidencia/provenance y las refs remotas permitidas, y la vista cambia mediante un resultado tipado sin recargar la página.
- **CA-LSI-04 — Inventario separado.** Dadas tres identidades diferentes, cuando se renderiza la tarjeta global, entonces `published`, `downloaded` e `installed` muestran valores, freshness y provenance propios; ningún valor/evidencia ausente se reemplaza por el de otra fila ni por `0.0.0`.
- **CA-LSI-05 — Estados y precedencia.** Para cada relación `updated`, `update-available`, `checkout-behind`, `ahead`, `installed-misaligned` y `unknown`, la UI muestra etiqueta y acciones coherentes. Si falla la autoridad, el estado primario es `offline` y una relación cacheada solo aparece como `lastKnownRelation`; no depende solo de color.
- **CA-LSI-06 — Check manual.** Dado el Launcher disponible, cuando el operador pulsa “Comprobar ahora”, entonces se reutiliza/coalesce el runner de check, se muestra estado cancelable/acotado y al terminar se actualiza el inventario sin iniciar plan ni apply.
- **CA-LSI-07 — Plan read-only.** Dado `update-available`, cuando se solicita plan con una política de cierre elegida, entonces se muestra el `UpdatePlan` sellado con target, commit/ref, precondiciones, fases, warnings, rollback/recovery, digest, `operationId` reservado y expiración, y no se abre una transacción.
- **CA-LSI-08 — Confirmación vinculada.** Dado un plan vigente, cuando se abre la confirmación, entonces el diálogo muestra el snapshot exacto y un botón final específico para `close-only` o `close-and-restart`; apply envía el mismo digest/operationId/payload y un grant R-13.4 válido.
- **CA-LSI-09 — Helper externo e idempotente.** Dado un grant válido, cuando el servidor acepta apply, entonces consume el grant, lanza el helper externo y este reclama atómicamente el `operationId`/journal antes del ACK; repetir ese ID devuelve la operación existente. El proceso Launcher no ejecuta el engine mutante in-process.
- **CA-LSI-10 — Progreso bounded.** Dada una operación activa, cuando el runner emite fases, entonces la UI presenta sequence/fase/mensaje sanitizados, sustituye cualquier evento mayor de 4 KiB por `progress-truncated`, conserva como máximo 100 eventos o 64 KiB y consulta snapshot tras truncation/gap.
- **CA-LSI-11 — Cierre sin reinicio.** Dado un plan confirmado con `close-only`, cuando el helper llega al boundary de activación, entonces el Launcher cierra después del ACK durable, el helper espera la salida del PID dentro de su cota y no relanza ningún proceso.
- **CA-LSI-12 — Cierre con reinicio.** Dado un plan confirmado con `close-and-restart`, cuando la operación termina verificada, entonces el helper relanza explícitamente el Launcher, la sesión anterior no se reutiliza y la nueva instancia reconcilia journal, outcome e identidad instalada.
- **CA-LSI-13 — Reanudación.** Dado un browser cerrado, Launcher reiniciado o handoff incierto, cuando el operador vuelve a abrirlo, entonces status reconcilia `operationId`/journal/`updateOperationLock`, recupera el snapshot y no crea una segunda operación.
- **CA-LSI-14 — Recovery bifásico.** Dado `recovery-required`, cuando el operador selecciona `resume` o `rollback` y una policy de cierre sin default, entonces obtiene/revisa un recovery plan read-only y un grant nuevo; solo la petición confirmada posterior lanza helper y muestra el outcome observado.
- **CA-LSI-15 — Paridad.** Dados los mismos fixtures de instalación/release/journal, cuando CLI y Launcher invocan status/check/plan/apply/recover, entonces usan el mismo runner y producen estados, planes, errors y outcomes equivalentes, salvo formato de presentación.

### Validaciones y errores

- **CA-LSI-16 — Arranque offline.** Dado un remoto inaccesible y cache válida o stale, el Launcher arranca, muestra `state=offline`, conserva freshness/provenance por identidad y presenta la relación cacheada solo como `lastKnownRelation`; nunca presenta el dato como live ni aplica automáticamente.
- **CA-LSI-17 — Sin evidencia.** Dado que no existe cache ni se puede consultar el remoto, la vista muestra `offline` con `lastKnownRelation=null` e identidades desconocidas; con conectividad pero evidencia inválida muestra relación `unknown`. Ningún caso infiere “actualizado”.
- **CA-LSI-18 — Operaciones Git prohibidas.** En bootstrap, status, check y plan, un spy de command runner demuestra cero invocaciones a `checkout`, `merge`, `pull`, `rebase`, `reset`, `stash`, install o activación. Solo el fetch canónico permitido puede aparecer en refresh/check.
- **CA-LSI-19 — Deadline, cancelación y coalescing.** Dos checks concurrentes más refresh de arranque producen como máximo un fetch activo. Al vencer deadline, el proceso se cancela/recolecta y state pasa a offline; al cancelar manualmente conserva state/conectividad previos con `lastOutcome=cancelled`. No quedan handles/tareas sin límite.
- **CA-LSI-20 — Provenance inválida.** Si remoto/ref/commit no cumplen el contrato del incremento 1 con conectividad disponible, `lastOutcome=invalid-provenance`, relación/state quedan `unknown`, apply se deshabilita y no se intenta remoto alternativo; nunca se etiqueta offline.
- **CA-LSI-21 — Plan stale.** Si cambia estado, target, commit, instalación, precondición o restart policy entre preview y apply, el servidor rechaza con `plan_stale`/mismatch antes de lanzar helper y la UI obliga a planificar de nuevo.
- **CA-LSI-22 — Grants fail-closed.** Token ausente, expirado, replayed, de otra sesión/instalación/acción/payload o ya consumido recibe error estable y causa cero side effects. Dos applies concurrentes con el mismo token aceptan como máximo uno.
- **CA-LSI-23 — Spawn, ACK perdido y ACK tardío.** Si spawn falla antes de claim, Launcher permanece abierto y exige plan/grant nuevos. Si helper pudo reclamar pero ACK se pierde/vence, UI entra en `handoff_uncertain`, bloquea retry y reconcilia `operationId`/journal/`updateOperationLock`/proceso. ACK tardío se adjunta al mismo ID; solo ausencia demostrada más helper terminado habilita nuevo plan. El grant consumido nunca se reutiliza.
- **CA-LSI-24 — Operation lock y preflight.** Si el runner detecta `updateOperationLock` ocupado, dirty, detached, ahead/diverged o drift de release, la UI muestra error tipado y next step; no ofrece stash/reset/clobber ni reintenta apply silenciosamente. El `stateWriteLock` no se interpreta como autorización para continuar.
- **CA-LSI-25 — Cancelación segura.** En una fase `cancellable`, cancelar solicita parada cooperativa, espera ACK, fija `cancellationState=accepted` y solo presenta “Cancelado” tras reconciliar que no hubo activación. Desde la fase irreversible responde `cancellation_not_safe`, fija `rejected`, mantiene seguimiento y no altera el runner outcome.
- **CA-LSI-26 — Fallo y rollback.** Si el engine falla antes o después de activación, la UI representa exactamente `failed` o `recovery-required` y las fases de rollback recibidas; no cambia el outcome ni borra journal.
- **CA-LSI-27 — Fallo de relaunch.** Si la instalación termina verificada pero el relaunch falla, se informa instalación correcta más `relaunch_failed` y comando/paso manual sanitizado; no se revierte una instalación sana por ese único motivo.
- **CA-LSI-28 — Recovery offline.** Con red ausente, recovery solo habilita acciones que el runner declare posibles con artefactos locales. Una acción que requiera red queda deshabilitada con motivo, no se intenta de forma optimista.
- **CA-LSI-29 — Límites de entrada/salida/tiempo.** Método, content type, campo/tipo desconocido, body >256 KiB o timeout 5 s se rechazan antes del runner. Un evento >4 KiB se sustituye por `progress-truncated` sin encolar el original; cola/clientes/historial conservan caps. Fake clocks verifican fetch 10/30 s, handshake 5/10 s, drain 3/5 s, PID wait 15/30 s y relaunch ACK 10/30 s, sin procesos/handles huérfanos.
- **CA-LSI-30 — Errores sanitizados.** Respuestas/UI no contienen stack, token, cookie, URL con credenciales, stdout/stderr bruto ni path sensible. El diagnóstico local conserva solo campos permitidos y límites explícitos.
- **CA-LSI-31 — Sin red externa en tests.** La suite funciona con remoto, HTTP y helper locales; un guard de red hace fallar cualquier conexión que no sea loopback o fixture autorizado.

### Permisos y visibilidad

- **CA-LSI-32 — Sesión.** Todas las rutas de inventario, operación, progreso y recovery requieren cookie de sesión válida. Reiniciar invalida la cookie y tokens anteriores sin perder el journal global.
- **CA-LSI-33 — Host/Origin.** Host incorrecto se rechaza; POST y stream/poll mutante sin Origin exacto se rechazan; no existe CORS wildcard ni preflight cross-origin.
- **CA-LSI-34 — Scope derivado.** Manipular body/query no permite elegir home, checkout, prefix, shim, executable, remote, ref arbitraria ni otra instalación. Esos valores proceden del contexto server-side y de planes validados.
- **CA-LSI-35 — Visibilidad global.** La tarjeta se identifica como actualización de la instalación global y mantiene el mismo estado al cambiar de proyecto. Si muestra runtime del proyecto, aparece como dato separado.
- **CA-LSI-36 — Botones honestos.** Apply queda oculto o deshabilitado con razón cuando no hay plan, hay operación activa, engine no disponible, estado unknown/offline no verificable o recovery pendiente. Recovery solo aparece cuando el runner lo autoriza.
- **CA-LSI-37 — Confirmación no persistente.** Token y estado de confirmación no se guardan en localStorage, URL, logs ni journal de frontend. Recarga, navegación, edición o nueva sesión obligan a obtener otro grant.

### Estados y efectos observables

- **CA-LSI-38 — No auto-apply.** Con una release disponible y dejando el Launcher abierto durante cualquier periodo, no aparece helper, journal de apply, cambio de shim/manifest/HEAD ni reinicio sin interacción preview→confirmación.
- **CA-LSI-39 — No-mutación de lectura.** Snapshots de worktree, branch/HEAD, instalación, shim, manifest transaccional y journal son idénticos antes/después de bootstrap local, status y plan. Check solo puede alterar refs/cache expresamente permitidas.
- **CA-LSI-40 — Handoff observable.** Antes de cerrar existe evidencia durable de helper ack, PID/operationId y plan digest. Después del cierre, el helper demuestra que esperó la terminación del PID antes de activar.
- **CA-LSI-41 — Eventos stale.** La UI ignora responses/events con requestId o sequence anterior, detecta gaps y vuelve a consultar snapshot; nunca retrocede visualmente a una fase antigua ni habilita un botón por evento stale.
- **CA-LSI-42 — Cierre de pestaña.** Cerrar la pestaña no emite cancel implícito. Al reabrir, una operación aceptada continúa o muestra su outcome/recovery sin duplicación.
- **CA-LSI-43 — Accesibilidad verificable.** Un recorrido solo teclado puede comprobar, planificar, cancelar, confirmar, inspeccionar progreso y recovery; foco vuelve al disparador, mensajes relevantes usan `aria-live`, reduced motion se respeta y estado/warnings no dependen solo de color. La evidencia procede de suite DOM/browser existente confirmada o de protocolo manual reproducible que registre herramienta, versión y pasos; una captura estática no basta.
- **CA-LSI-44 — Regresión R-13.4.** Las suites de auth, same-origin, schemas, límites, grants, SSE y no-mutación existentes siguen pasando junto con la matriz nueva.
- **CA-LSI-45 — Review de duplicación.** La revisión independiente confirma que handlers/static no contienen comandos Git, parsing SemVer, writes de manifest/journal, implementación de `stateWriteLock`/`updateOperationLock`, lógica de rollback ni taxonomía paralela.
- **CA-LSI-46 — Handoff a 5/5.** La evidencia final identifica casos, plataformas ejecutadas, limitaciones y resultados focales para que el incremento 5 pueda certificar release/CI/docs sin reinterpretar outcomes.
